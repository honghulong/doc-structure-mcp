## 2. 记录原则

- 每次测试必须记录模型、运行环境、输入样本、关键参数、耗时、输出文件和人工结论。
- 真实文书内容必须脱敏；日志中只保留必要字段、结构问题和结论。
- 不只看 OCR 文本，还要记录 bbox、阅读顺序、表格还原和多页处理情况。
- 测试失败也要记录，尤其是安装失败、显存不足、超时、PDF 渲染异常和输出结构异常。

### 9.2 三模型结果

| 模型名 | 检测模型 | 识别模型 | 行数 | 平均置信度 | 低置信度数 | 推理耗时 | 人工结论 |
|---|---|---|---:|---:|---:|---:|---|
| `mobile` | `PP-OCRv5_mobile_det` | `PP-OCRv5_mobile_rec` | 55 | 0.9811 | 1 | 4046ms | 文字主体可用，但标题/税务局区域碎框和噪声更多 |
| `mid` | `PP-OCRv5_server_det` | `PP-OCRv5_mobile_rec` | 49 | 0.9831 | 0 | 2118ms | bbox 与速度表现较好，但有个别识别错字 |
| `server` | `PP-OCRv5_server_det` | `PP-OCRv5_server_rec` | 49 | 0.9825 | 1 | 3088ms | 综合最好，关键字段、标点和税务局文字更稳 |

本轮人工排序结论：

```text
server > mid > mobile
```

其中 `mid` 的意义是单独观察 `server_det` 对 bbox 的提升，`server` 的意义是同时观察 `server_det + server_rec` 的完整效果。

### 9.3 与本地 8765 OCR 服务对比

本地 `8765` 服务来自 `D:\hongmengProjects\ocr-invoice-mcp\src\ocr_server.py`，不是纯 OCR 服务。它返回：

| 字段 | 含义 |
|---|---|
| `ocr_raw` | 接近 PaddleOCR 原始文本块结果，包含 text/confidence/bbox |
| `ocr_text` | 从 `ocr_raw` 过滤置信度后拼接的文本 |
| `invoice_fields` | 发票字段后处理结果 |
| `tables` | 表格识别结果；当前 table engine 未启用时为空 |

若比较 OCR 质量，应比较：

```text
8765.ocr_raw vs Colab pages[0].lines
```

本轮观察：Colab `server` 原始 OCR 行数更少、平均置信度更高、耗时更低，原始 OCR/bbox 质量优于本地 8765；但 8765 有发票字段提取后处理，适合业务字段读取，不适合作为纯 OCR 能力对比对象。

### 9.5 竖排观察

三模型均正确识别了以下竖排文字：

```text
购买方信息
销售方信息
备注
```

但 OCR JSON 只返回完整字符串和高窄 bbox，不返回显式方向字段。因此本地 `src/layout_preview.py` 增加通用竖排判断：

| 条件 | 当前值 |
|---|---|
| 文本长度 | 2 到 8 |
| 中文占比 | 不低于 75% |
| bbox 高宽比 | `h/w >= 1.8` |

命中后 HTML 使用 `writing-mode: vertical-rl` 和 `text-orientation: upright` 竖排显示。

该规则已经在三份 HTML 中命中 3 个竖排块。

### 9.6 坐标精度观察

overlay 中部分框看起来比原字高或低，初步判断不是单一 bug，而是以下因素共同导致：

- OCR bbox 是文本检测区域，不是字符精确外轮廓。
- PaddleOCR 检测框通常带有余量，以避免切字。
- 四点 bbox 当前在 HTML 中用外接矩形表达，倾斜或旋转时会偏大。
- PDF 渲染为图片后，bbox 坐标对应渲染图像坐标，不是 PDF 原始坐标。
- overlay 中 OCR 文字由浏览器重绘，字体和原图不一致，不能逐像素对齐。

后续评价应优先看 bbox 是否覆盖原文字块、是否漏框、是否粘框，而不是要求覆盖文字与底图完全贴合。
